## 官方能力与限制

官方支持创建持久线程、按 thread_id 恢复，以及在同一线程继续 turn；这不要求自行编译 Codex。上下文会自动压缩，自动压缩阈值默认来自模型设置，也有显式 compact 接口。应监听压缩生命周期事件，不能把 compact 请求返回成功当作已经压缩完毕。[App Server](https://learn.chatgpt.com/docs/app-server)、[配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)。

官方建议同一连贯工作保留在同一聊天，也提醒混入过多不同工作会使上下文膨胀。压缩保留的是供后续推理使用的摘要，不能保证一天内每句话、每个数字仍完整可见。[最佳实践](https://learn.chatgpt.com/docs/learn/best-practices)。

持久线程增加会话落盘。应在实施时核对实际 rollout、状态数据库、日志及认证目录，优先把项目会话数据置于 E 盘，并保留用户现有 Codex 登录与个人会话。history.jsonl 的历史开关与线程 rollout 不是同一概念，不能据此推断持久线程已被禁止或已被删除。[高级配置](https://learn.chatgpt.com/docs/config-file/config-advanced)。

当前安装版本为此前核对的 0.164.0；本次官方文档描述当前接口，不能把新文档里所有新字段直接用于旧版本。实施前须对安装版本验证 start/resume、动态工具、压缩和路由。尤其不把当前文档的 thread/inject_items 作为旧版本必备依赖；可先通过下一轮输入携带记忆增量。

## 方案比较与建议

| 方案 | 对本项目的影响 | 判断 |
| --- | --- | --- |
| 每次模型调用新临时线程 | 上下文容易控制、辅助调用彼此隔离；工具链和长对话只能依赖程序反复重组，最近窗口之外的未整理内容容易接不上 | 普通聊天值得改进；独立抽取等辅助用途仍适合短会话 |
| 全部私聊、群聊、任务共用一个持久线程 | 自然能看到已输入内容，但不同聊天、身份和权限混合，跨群消息争用活动 turn，长任务会拖住聊天，抽取/反思也会污染日常对话 | 不建议 |
| 每聊天持久线程 + 共享记忆与近期经历 + 独立任务线程 | 同一场景保持连续，同时通过共享层维持白璎统一经历与人物认知，任务独立续跑 | 建议作为后续实现方案 |

这是结合本项目调用路径的架构判断，不是官方保证性能一定更快。持久线程减少手工拼接和重复历史的机会，但上下文变大仍会增加处理量；实际延迟、额度消耗和召回效果须对照测试。

### 线程与调用用途

- 普通对话：按 body + channel + 会话代次保存 thread_id，同一聊天群内不同说话人共用该群线程，每条新增消息都带可靠身份与时间。
- 后台长任务：按 task_id 保存独立线程，存续可跨天；日常聊天轮换不直接抹掉任务上下文。停止进程后的任务状态明确记录为中断/可恢复，不能假称继续运行。
- 记忆抽取、反思、图片描述等：使用独立辅助会话，不把 JSON 摘要指令或其他聊天的工具结果追加到普通聊天线程。
- 同一线程内排队推进 turn；后台线程独立处理。事件和回调按 thread_id、turn_id、call_id 路由，所有工具仍用程序持有的 SkillContext 校验，不能靠模型记住当前权限。
- 改为新增消息、工具结果和记忆增量的投递；不能只改 ephemeral=false，然后每轮仍把整段最近历史重复追加。用事件 ID、记忆版本和同步游标去重。

### 私聊与群聊如何继续互通

采用三层：原始事件即时落盘；当前聊天在线程内保持日内连续；共享记忆层向各线程提供人物事实、白璎状态、当天相关经历与任务结果。

关键是增加“当天近期经历”的增量检索/同步，直接覆盖尚未整理成长期记忆的事件。这样用户在私聊告知普通信息，随后去群聊提问，以及反向顺序，都能按相关性接上，不需要先停机或等 30 分钟抽取。此处“增量”是程序记录和按需检索，不要求每条消息都额外调用模型总结。

每条共享内容保留来源、身份、时间和版本，作为回忆材料输入，不能升级为新的执行指令。群聊与私聊普通语义记忆的双向互通是明确验收项，不因分线程而单向化；原文记录、本机文件、屏幕和剪贴板等沿用既有各自的访问与临时性要求，不把文件夹合并或旧工具授权顺带传播。

现有全局检索已能跨聊天召回整理过的记忆，但“未整理的当天经历”仍需补通。仅依赖两个持久线程，或仅共享一份 SQLite 文件，都不会让另一线程自动知道新增内容，仍要在下一轮注入相关增量或提供可调用的记忆检索工具。

### 每日维护、主动停止与意外退出

支持用户希望的“日内保留上下文，重维护集中到日切或主动 stop”。不建议把原始事件保存、任务检查点也延迟到 stop；这两项继续实时落盘。

计划维护或主动 stop 的建议事务顺序：暂停接新工作并划定事件水位 → 收尾或中断活动 turn、保存任务检查点 → 按原始事件分批抽取未整理记忆并写入共享库 → 记录已整理游标和新代次 → 归档旧聊天线程 → 恢复服务/下次启动时按需新建线程并加载记忆。边界期间的新消息入队，不能丢失。

只有整理与游标提交成功才正常切换代次。超时、额度耗尽或强制终止时保留未处理事件和待整理状态，后续重试；不能显示“整理完成”后直接丢弃上下文。一天多聊天的积压可能超过现有 90 秒等待，需要分批处理、阶段状态与超时策略。掉电等意外退出无法保证执行 shutdown 回调，应优先恢复已有持久线程，不能误当主动 stop 直接换新。

长期记忆抽取必须以原始事件为准，不能只总结已被 Codex 压缩过的上下文。自动压缩解决当前推理的窗口容量，不替代人物档案、事实纠错、共享记忆、原文记录和任务状态。

“忘掉某事”也必须覆盖旧持久上下文：仅删长期记忆库还不够。实施时应通过受控重建/轮换受影响线程等方式移除旧输入及压缩摘要残留，并处理归档保留策略，不能依靠一句“请忘记”保证。

DeepSeek 兜底仍使用共享事件与记忆构造输入。回到 Codex 后按游标补入兜底期间的新对话和工具结果；请求已执行但响应丢失时先核对，不盲目重复工具调用或发送消息。

## 后续验收重点

1. 同一天超过现有最近消息窗口、跨多轮工具调用后仍能接续；发生自动压缩后能按原文核验数字、页码与任务要求。
2. 私聊刚说过的普通信息，群聊立即能回忆；群聊刚发生的事，私聊立即能接上。两方向均不依赖停机、日切或会话空闲。
3. 多群、私聊、记忆抽取和后台长任务同时发生，不串回复、不串工具权限；长任务不堵普通聊天。
4. 主动 stop、计划日切、进程崩溃、抽取超时、订阅限流分别验证；检查恢复后的游标、状态、未发通知以及文件操作是否重复。
5. 纠正或忘记后，新线程与受影响持久线程不再沿用旧事实；当前文件/历史/临时内容边界保持。
6. 订阅转兜底再转回后，双方都知道切换期间发生的事；对照记录延迟、额度、上下文大小及共享记忆命中率。

## 本次结论

持久线程适合本项目普通聊天与持续任务，建议采用；采用每聊天持久线程、任务独立线程，并保留共享记忆及新增当天增量同步。日切/主动 stop 集中整理长期记忆可以作为目标，但实时事件保存、跨聊天近期记忆同步和异常恢复仍需保留。具体固定时间沿用配置候选（默认睡眠 04:00），不在调研阶段新增系统计划任务或改变现有维护行为。
